Known differences from R limma
==============================

pylimma is validated against R limma using pre-computed CSV fixtures
generated by ``tests/fixtures/generate_all_fixtures.R``. The target
tolerance is ``rtol=1e-6, atol=1e-12`` for deterministic statistics,
and a log10-scale comparison for p-values.

The sections below document every numerical gap that remains after
porting.

Accepted differences
--------------------

Four differences remain after porting. All four are statistical
artefacts of numerical-algorithm choices, not porting bugs. All are
quantified, reproducible, and inside published tolerances.

normexp saddle-point fit drifts up to ~2e-4 from R
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``normexp_fit(method="saddle")`` parameters match R within
``rtol ~2e-4``; the objective function value agrees to
``rtol ~6e-9``. ``method="mle"`` matches R to ``rel ~2e-13``;
``method="rma"``, ``method="rma75"``, and ``normexp_signal`` all match
R at floating-point precision.

**Root cause.** scipy's Nelder-Mead and R's ``nmmin`` share the same
algorithm and initial simplex but use different termination rules. R
uses a relative f-range ``VH - VL < intol * (|VL| + intol)`` with
``intol = sqrt(eps) = 1.49e-8``, giving ``convtol ~4e-4`` at the
saddle objective scale (``f ~ 25000``). scipy uses absolute
``fatol=1e-4`` and ``xatol=1e-4``. scipy consequently runs a few
iterations further and lands at a slightly better f at a different
point on the flat saddle-likelihood plateau.

**Tolerance.** Parity tests for ``method="saddle"`` use
``rtol=1e-3``. All other normexp methods are at ``rtol=1e-10`` or
better.

normalize_vsn output drifts up to ~2.4e-4 from R/vsn 3.66.0
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``normalize_vsn`` matches R's ``normalizeVSN`` (which delegates to
the Bioconductor ``vsn`` package) within ``rtol ~2.4e-4``. The
transform formula and ``hoffset`` rescaling are bit-faithful: at
R's converged parameters pylimma reproduces R's output to
``rtol ~1e-7`` (verified by
``TestNormalizeVSNRParity::test_transform_at_r_params_matches_r_to_machine_precision``).
The remaining drift comes entirely from the L-BFGS-B optimisation
step.

**Root cause.** The vsn profile log-likelihood is asymptotically
flat under a uniform shift in the per-column scale parameter
``b``. In the large-``y`` limit ``arsinh(z) ~ log(2 z) = log(2) +
b + log(y)``, so a uniform shift adds the same constant to every
transformed cell, the row-mean centring absorbs it, and the
per-stratum ``hoffset = log2(2 * exp(mean(b)))`` rescaling absorbs
it again at the end. The likelihood becomes asymptotically flat
under that direction. R/vsn calls LINPACK's ``lbfgsb`` and
pylimma calls ``scipy.optimize.minimize(method="L-BFGS-B")``;
under the same loose convergence tolerances the two
implementations land at different points along the flat valley
despite reporting near-identical negative log-likelihood
(typically agreeing to four decimal places). Because the
absorption is exact only asymptotically, the residual disagreement
in the *transformed output* at finite ``y`` is the figure quoted
above.

**Tolerance.** Parity tests for ``normalize_vsn`` use
``rtol=5e-4`` for the end-to-end output and ``rtol=1e-6`` for the
transform-at-R-params verification.

**Note.** Because the likelihood is genuinely flat in this
direction the divergence is irreducible without a regularisation
term breaking the flat direction (which would itself be a
deviation from R). pylimma chooses ``b=0`` (unit scale factor) as
the L-BFGS-B starting point rather than R/vsn's ``b=1``: with
``b=0`` scipy's optimiser stays in the same valley region as R's,
giving the ``2.4e-4`` figure above; with ``b=1`` (R's
``pstartHeuristic``) scipy walks to the opposite end of the
valley, giving ``rtol ~4e-3``. This is a deliberate divergence
from R's heuristic; ``pstart`` is documented as a heuristic in
``vsn/R/vsn2.R`` and is not exposed by limma's
``normalizeVSN.default``, so the change is invisible to limma
users.

Monte-Carlo rotation tests (``roast``, ``mroast``, ``romer``, ``gene_set_test``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Rotation-based gene-set tests draw rotations from NumPy's PCG64 RNG.
R uses the Mersenne Twister inside its own ``sample.int`` / ``rnorm``
C routines. The two streams cannot be aligned byte-for-byte from the
same seed. Deterministic summaries match R to ``rtol=1e-15``:

- ``ngenes_in_set``
- observed test statistics
- active proportions ("PropDown" / "PropUp")
- the rotated-effects matrix when the rotation seed is matched
  post-rotation (e.g. via ``compare_pvalues(max_log10_diff=0.5)``)

Monte-Carlo p-values from ``roast`` / ``mroast`` / ``romer`` /
``gene_set_test`` agree with R within sampling error.

**Tolerance.** Empirically ~0.3 log10 (factor of 2) between R and
pylimma at ``nrot=999`` on the gene-set-testing fixture data, well
inside the documented ``max_log10_diff=0.5`` threshold.

mrlm stdev_unscaled drifts up to ~15% on machine-epsilon residuals
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

When a gene is perfectly fit by the design (initial OLS residuals at
machine epsilon), ``mrlm`` and R ``MASS::rlm`` produce different
``stdev_unscaled`` values - up to 15% relative difference. The trigger
is exclusive to synthetic perfectly-fit rows; real proteomics or
RNA-seq residuals are 6+ orders of magnitude above machine epsilon
and unaffected.

**Root cause.** R's ``lm.wfit`` uses LINPACK ``DQRDC2`` which produces
mixed-sign machine-epsilon residuals on a degenerate row. scipy's
``np.linalg.lstsq`` uses LAPACK SVD which produces uniform-sign
residuals. The iter-1 MAD scale picks up R's mixed-sign noise pattern
and Huber-downweights three samples as "outliers"; pylimma's MAD
gives unit weights everywhere and returns the unweighted OLS stdev.
Both implementations are computing deterministic numerical noise -
just different noise patterns - because the residuals carry no
information about the underlying linear model.

**Tolerance.** A regression sentinel test
(``tests/rigorous/test_mrlm.py::test_b9c_zero_residual_scale``) is
left as ``xfail`` rather than loosened, so any future numerical
change that aligns the two patterns is detected automatically.

**Note.** Downstream impact is zero: when a row hits this regime
``sigma`` is also at machine epsilon, t-statistics are inf/NaN,
and the empirical-Bayes posterior is dominated by the prior
regardless of which "garbage" stdev was returned.

Deliberate divergences: intended rather than literal R behaviour
----------------------------------------------------------------

Where R limma contains a clear bug, pylimma follows the behaviour the
limma code evidently intends rather than reproducing the bug. Each
case below is tested against a reference computed in R with the
single-line correction applied, and the literal R behaviour is
recorded in the fixtures alongside it.

decide_tests: hierarchical method with a supplied genewise_p_value
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

For a matrix of p-values, ``decideTests.default(method="hierarchical",
genewise.p.value=...)`` in limma 3.66.0 fails with
``object 'ngenes' not found`` for every ``adjust.method`` except
``"none"``. ``ngenes`` is defined only inside the branch that
computes Simes genewise p-values when none are supplied, but the
p-value cut-off multiplier uses it in both cases.

pylimma uses ``ngenes = nrow(p)`` in both cases. The reference
fixtures (``R_dt_p_hierarchical_genewise_*_intended.csv``) come from
R's ``decideTests.default`` with ``ngenes <- nrow(p)`` inserted before
its ``switch()``; the fixture script checks that the patched function
reproduces R exactly wherever R itself succeeds.

genas: logFC / predFC subsets re-centre the coefficients
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

In ``genas(subset="logFC")`` and ``genas(subset="predFC")``, limma
assigns the re-centred coefficients to ``fit$coeff``. R's ``$<-`` does
not partial-match, so this creates a new list element and the
re-centring never reaches the likelihood, which reads
``fit$coefficients``. pylimma applies the re-centring as the code
intends.

fit_f_dist_unequal_df1: two informative values with zero prior weights
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

With exactly two informative variances, ``fitFDistUnequalDF1`` sets
``prior.weights <- NULL`` to fit them without weights. But
``PriorWeights <- !is.null(prior.weights)`` has already been computed, so
if any prior weight existed - including the zero weights the function
itself creates for missing ``x`` or ``df1 < 0.01`` - limma 3.66.0
multiplies by ``NULL`` and returns ``scale = NaN``. pylimma clears the flag
together with the weights. The reference is R's function with
``PriorWeights <- !is.null(prior.weights)`` repeated after the reset;
``tests/rigorous/test_fit_f_dist_unequal_df1.py`` checks that unpatched R
returns NaN and that pylimma matches the patched function.

voom_with_quality_weights: sample weights when genes equal samples
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``voomWithQualityWeights`` passes the estimated sample weights to its
second ``voom`` as a plain vector. ``asMatrixWeights`` reads a vector whose
length equals the number of genes as gene (probe) weights before it
considers array weights, so when there are exactly as many genes as
samples R uses the sample weights as gene weights. pylimma passes them as
a 1 x N row matrix, which is always read as array weights. The reference
fixtures (``R_vqw_square_*_intended.csv``) come from R's steps with that
one change; the fixture script checks that they reproduce
``voomWithQualityWeights`` whenever the number of genes differs from the
number of samples.

Names of unnamed gene sets
~~~~~~~~~~~~~~~~~~~~~~~~~~

For an unnamed list of gene sets, R's ``mroast`` and ``fry`` name the sets
``set1``, ``set2``, ... (zero-padded from ten sets: ``set01``), while R's
``camera``, ``cameraPR`` and ``romer`` leave them unnamed, so their result
rows are labelled ``"1"``, ``"2"``, .... pylimma uses the ``set1`` naming in
all of them, so results of different tests can be joined on the set name.
A single set passed on its own is ``set1`` (``romer``: ``set``, as R).

gene_set_test simulation: exact ties
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

With ``ranks_only=False``, ``geneSetTest`` counts random sets whose mean is
at least the observed mean, so ties are decided by rounding. R's ``mean()``
sums in long double: on Linux (x86-64, extended precision) a permutation of
the same values ties exactly, and a set of all genes gives p = 1, but on
platforms where long double is ordinary double (e.g. macOS on Apple
silicon) the same call gives values such as 0.999 or 0.5. pylimma compares
exactly rounded means (``math.fsum``), so ties are always exact and the
result does not depend on the platform; it agrees with R on Linux.

``top_go`` / ``top_kegg``: order of names tied on p-value and size
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Rows tied on both p-value and number of genes are ordered by term or
pathway name. R's ``order()`` compares text with the collation of the
user's locale (in ``en_GB``: apoptosis, Apoptosis, b, Wnt signaling);
pylimma compares by code point (Apoptosis, Wnt signaling, apoptosis, b),
as R does in the ``C`` locale, so the order is the same on every machine.

``make_contrasts`` without contrasts
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

With no contrasts, ``make_contrasts`` raises "No contrasts specified". R's
``makeContrasts`` returns a matrix with one row per level and no columns for
``contrasts = character(0)``, and fails with "length of 'dimnames' [2] not
equal to array extent" when ``...`` is empty. pylimma reports the missing
contrasts where they arise instead of returning a matrix with no columns.
``generate_all_fixtures.R`` records the R behaviour.

Clear errors where R fails obscurely or behaves accidentally
------------------------------------------------------------

For some invalid or degenerate inputs, R limma either stops with a
message from deep inside the computation or returns a result produced by
accident (for example by recycling or by ``NULL`` propagation). pylimma
raises a ``ValueError`` that names the problem instead. Valid inputs are
unaffected.

``decide_tests`` with ``method="hierarchical"`` or ``"nestedF"`` on a fit without F-statistics
    ``e_bayes`` computes F only when the fit has a full-rank design. R's
    ``decideTests`` then passes ``F.p.value = NULL`` to ``p.adjust()``,
    selects nothing and returns all zeros; pylimma raises an error saying
    that F-statistics are needed. ``generate_all_fixtures.R`` records the
    R behaviour.

``remove_batch_effect`` with a missing ``batch`` / ``batch2`` label
    A missing label (``None``, pandas NA, a categorical NaN) raises "batch
    contains missing labels". R's ``as.factor`` leaves NA out of the levels,
    and ``removeBatchEffect`` then stops with "not enough degrees of freedom
    to define contrasts" or "number of rows of matrices must match". As in
    R, a numeric NaN is not missing but a level of its own.

``remove_batch_effect`` with ``batch`` / ``batch2`` / ``covariates`` of the wrong length
    Raises "<argument> has <k> rows/values, but there are <n> samples"
    (R: "number of rows of matrices must match (see arg 2)" from ``cbind``).

Character gene sets without gene IDs (``roast``, ``mroast``, ``fry``, ``camera``, ``camera_pr``, ``romer``)
    A set given as gene IDs needs IDs to match against: the row names of
    ``y`` (``adata.var_names``, a DataFrame index) or ``geneid=``. Without
    them pylimma raises an error; R matches against ``NULL`` row names and
    silently tests an empty set. Likewise ``gene_set_test``,
    ``wilcox_gst`` and ``rank_sum_test_with_correlation`` select a character
    set by the names of ``statistics`` (a pandas Series) and raise an error
    for a name that is not among them, where R's ``statistics[name]`` is NA
    and the p-value silently NA.

``camera`` / ``romer`` with missing or infinite values
    Raise "All y values must be finite and non-NA" (the wording of R's
    ``.lmEffects``); R stops in its Fortran QR with "NA/NaN/Inf in foreign
    function call".

``nrot`` / ``nsim`` in ``roast``, ``mroast``, ``romer`` and ``gene_set_test``
    Must be whole numbers of at least 1 (whole-number floats such as
    ``1e4`` are accepted). Below 1, R fails with "invalid 'nrow' value" or,
    for ``geneSetTest``'s ``nsim``, returns ``Inf``; for a fraction such as
    10.5, R recycles random numbers into a 10-row rotation matrix and uses
    10.5 in the p-value denominators, which is not meaningful.

``top_table`` / ``top_table_f`` with ``number=NaN``
    Raises "number must not be NaN" (R: "missing value where TRUE/FALSE
    needed"). Other values of ``number`` follow R: capped at the number of
    rows, an empty table below 1, and truncation of a non-integer.

``fit_gamma_intercept``
    Missing values in ``y`` or ``offset`` raise "y and offset must not
    contain missing values", and a Newton step that is 0 / 0 (an offset
    of zero where ``y`` is zero) raises "Newton step is undefined"; R
    stops with "missing value where TRUE/FALSE needed" in both cases.
    ``offset`` must be a scalar or have the same length as ``y``; R
    accepts other lengths (recycling a non-constant offset, ignoring the
    length of a constant one).

``top_go`` with an ``ontology`` element that matches nothing
    Raises "'arg' should be one of ...". R's ``match.arg(several.ok =
    TRUE)`` silently drops such an element when another element matches
    (``ontology = c("BP", "XX")`` gives BP only). Abbreviations such as
    ``"B"`` work in both. ``generate_all_fixtures.R`` records the R
    behaviour.

``goana`` / ``kegga`` with set names that differ only in case
    The output columns are the lower-case set names (``up``, ``p_up``), so
    two sets such as ``"A"`` and ``"a"``, or a set named ``"N"`` next to the
    ``n`` column, raise an error naming the clash. R keeps the names as
    given (``A``, ``a``, ``P.A``, ``P.a``). Previously pylimma silently kept
    only one of the sets.

``goana_trend`` with invalid ``index_de`` positions
    Positions must be whole numbers between 0 and ``len(covariate) - 1``
    (or ``index_de`` a boolean mask). R's ``isDE[index.de] <- 1`` treats a
    negative position as "all except", truncates a fraction and silently
    extends ``isDE`` for a position past the end. ``generate_all_fixtures.R``
    records the R behaviour.

``top_go`` / ``top_kegg`` with ``number=NaN``
    Raises "number must not be NaN", as ``top_table`` does (R: "missing
    value where TRUE/FALSE needed"). Other values of ``number`` follow R.

``make_contrasts`` with levels that are not names, or duplicated names
    ``levels`` must give the parameter names: a list of strings, a
    categorical or a design matrix with column names. A matrix without
    column names or numeric values raise an error (R: "argument is of
    length zero"). Duplicated names raise an error; R assigns the
    indicator to the last copy only, so the other copies get zero in every
    contrast. ``generate_all_fixtures.R`` records the R behaviour.

``make_contrasts`` with names other than the levels
    Contrast expressions may use the level names, numbers, ``+ - * / ^``
    and brackets; any other name or a function call raises an error naming
    it. R evaluates the expression in the R session, so ``pi`` and R
    functions such as ``mean(c(A, B))`` work, and a name that is not a
    level resolves to whatever object of that name R finds (``B - D``
    fails with "non-numeric argument to binary operator" because ``D`` is
    ``stats::D``). A contrast given as a number rather than a string
    (``make_contrasts(B=1, ...)``) raises an error; R fills the column with
    the number. The level names ``...`` and ``..1`` raise an error: they
    pass ``make.names()``, but R cannot evaluate them ("'...' used in an
    incorrect context"). An expression over several lines raises an error;
    R parses each line as its own expression and keeps only the last
    (``"A + B\n- C"`` is ``-C``). ``generate_all_fixtures.R`` records the R
    behaviour.

Formula strings containing ``^`` (``model_matrix``, ``lm_fit``, the ``voom`` family)
    Raise an error asking for ``**``. pylimma builds designs from formulas
    with patsy, which evaluates ``I(x^2)`` as Python's bitwise XOR (silently
    wrong numbers for an integer column) and rejects ``(a + b)^2``. In
    patsy, ``I(x**2)`` is R's ``I(x^2)`` and ``(a + b)**2`` is R's
    ``(a + b)^2``. A ``^`` inside a quoted name (``Q("a^b")``) is allowed.

Deliberate interface difference: EList design and weights slots
---------------------------------------------------------------

R's ``voom`` and ``voomWithQualityWeights`` call ``as.matrix()`` on an
``EList`` input, which silently drops every slot except ``E``. pylimma's
``voom`` uses the EList's ``design`` and ``weights`` slots, and
``voom_with_quality_weights`` its ``design`` slot, when the caller does
not pass them explicitly, and emits a ``UserWarning`` each time so that
code ported from R does not change results unnoticed. Passing
``design=`` / ``weights=`` explicitly reproduces R exactly. ``vooma``
matches R.

``vooma_lm_fit`` uses an EList's ``weights`` slot as ``prior_weights``
throughout, again with a ``UserWarning``. R's ``voomaLmFit`` passes the
EList to its first ``lmFit``, which falls back to ``y$weights``, and drops
the slot for every later fit, so the slot affects only the initial fit.
Because pylimma treats the slot as prior weights, ``sample_weights=True``
with a weights slot raises an error, as it does with ``prior_weights=``.

``array_weights`` uses an EList's ``design`` slot when ``design=`` is not
given, with a ``UserWarning``. R's ``arrayWeights`` documentation says the
design is "extracted from the data object if available", and its
``getEAWP`` call returns it, but the code never reads it and uses an
intercept-only design. pylimma follows the documentation;
``generate_all_fixtures.R`` records R's literal behaviour.
